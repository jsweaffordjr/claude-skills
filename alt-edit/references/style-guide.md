# Visual style defaults

These are the standing defaults for Jerry's alt channel (biblical health / carnivore
diet), refined across three videos. Font sizes live in `scripts/gen_overlay.py` -- don't
re-derive them from scratch, use that script, and read its module docstring for the
current numbers and history.

**The 4x default is a starting point per video, not a guarantee -- check every time.**
Video 3 ("Objections to Carnivore") ran noticeably tighter than videos 1-2: chin
routinely reached 78-85% of frame height (vs ~87% only in the worst single frame of
video 2). At the standard 4x size, both scripture AND badges overlapped his chin in
real composite tests. The fix was an emergency-shrink similar to video 2's 1 Kings 19
case, but this time it hit badges too -- `gen_overlay.py badge` didn't support
`--label-size`/`--body-size` overrides until this video needed them; it does now. Don't
assume badges are exempt from the sizing problems scripture runs into -- check both.

**Motion graphics need the same size flexibility as text overlays.** Video 3's three
motion graphics were originally designed at fixed pixel dimensions (~420-760px tall)
copying video 1-2's scale, and all three had to be redesigned smaller (~220-230px)
after the safe-zone check failed. Design motion graphics with adjustable W/H and font
constants from the start (easy to scale a few numbers down) rather than hardcoding
values that assume a video 1-2-style safe zone. A 5-row vertical checklist (the first
blood-panel draft) didn't fit the tighter budget at all and needed a different
layout (horizontal chips) -- sometimes the fix isn't "make it smaller," it's "use a
different shape" for the same content.

**Sizing history**: original -> 3x (still too small) -> scripture text doubled again
to 4x original after the second video (badges stayed at 2x, that size was fine both
times). This 4x default is specific to alt-edit's tight close-up footage -- main-edit
tried inheriting it and found it oversized on its calmer seated shot, then landed back
on the 3x size (138/126) as ITS correct default, in true on-screen proportion. Font
size that reads right depends on the footage style, not just on "bigger = more
readable" -- don't assume one channel's validated size transfers to another without
checking in context. See main-edit's SKILL.md for that channel's separate default.

**Check for text overflowing its OWN card/badge canvas, not just face overlap.** The
safe-zone composite check (below) verifies text doesn't sit over the speaker -- it says
nothing about whether the text itself clips against the card/badge's own edges. Confirmed
on the WhatYouStopEating video (2026-09): at the 4x scripture default (`--label-size 276`),
longer references like "PROVERBS 23:31-32 (WEB)" had their trailing "(WEB)" clipped off
the right edge of a 2560px-wide card, while a short one ("GENESIS 9:3 (WEB)") happened to
fit -- so a single visual spot-check on one reference isn't enough. Separately, the
"EAT BIBLICALLY" badge text measured ~934px wide against `gen_overlay.py badge`'s default
900px canvas at `BADGE_FONT_SIZE=116` -- wider than its own canvas, overflowing both edges
-- while shorter badges ("FAST WEEKLY", "WALK DAILY") looked fine. Before finalizing sizes,
measure actual rendered width via `PIL.ImageDraw.textlength` against the card/badge width
for the *longest* label/badge text in that specific video (not a representative one), and
treat clipping as a hard stop the same as a face-overlap failure.

**Never judge a candidate font size from an isolated, cropped card PNG** -- shown alone
with nothing else in frame, text reads as far larger than it will once placed in the
actual 4K video. This caused real back-and-forth confusion when picking main-edit's
size: sizes shown as cropped images all read as "too large," but the same sizes
composited onto a real frame (`overlay=X:Y` onto an actual footage frame, same as the
safe-zone check) immediately clarified which one actually looked right. Always
composite size candidates onto a real frame before asking Jerry to compare them.

At 4x, even a modest single verse can run 1200-2000px+ tall at normal card
widths -- see "Scripture chunking" below, this is expected and handled by splitting
text shorter, not by fighting the font size.

## The three graphic types

1. **Scripture lower-thirds** -- when Jerry references or quotes a Bible passage.
   Reference (e.g. "MATTHEW 7:13-14 (WEB)") in gold bold sans, verse text in white
   serif italic, on a semi-transparent near-black rounded bar with a gold left accent
   stripe. Generated by `scripts/gen_overlay.py scripture`.

2. **Keyword/framework badges** -- when Jerry names a recurring concept or step from
   whatever framework the video is about (video 1: the "FEW" fast-weekly/eat-biblically
   /walk-daily framework; video 2: "Mistake 1/2/3 + Bonus" -- future videos may have a
   different structure or none at all; ask Jerry what the key terms are). Two forms,
   both via `scripts/gen_overlay.py badge`:
   - Short (2-3 words, e.g. "FAST WEEKLY"): single-line pill.
   - Longer (a phrase/sentence, e.g. "MISTAKE 2" + "Jumping into longer fasts too
     quickly"): two-tier card via `--body`, same label+body grammar as scripture cards.
     Use this whenever the text won't comfortably read as one line at badge size --
     don't force a long sentence onto a single line, it just runs absurdly wide.

3. **Motion graphics** -- when Jerry describes something that's easier to *show* than
   read (video 1: an animated 12h-to-16h fasting gauge; video 2: a 3-step re-entry
   ladder, a 3-checkpoint gauge, and a heartbeat-pulse cue). No reusable script --
   each concept needs its own small bespoke animation. Build it as a sequence of
   PIL-rendered PNG frames (blank transparent background, draw only what's needed),
   then assemble into an alpha-channel `.mov` with:
   ```
   ffmpeg -framerate 15 -i frame_%04d.png -c:v qtrle -pix_fmt argb clip.mov
   ```
   15fps is plenty for a simple animated gauge/diagram; no need for 30fps. Keep it
   visually consistent with the other two graphic types: same gold/white/dark palette,
   same rounded/soft aesthetic, simple and readable over a moving outdoor background.
   For a progressive/sweeping animation, verify the timing lands where you think it
   does by computing it explicitly (video 2's first pulse-cue attempt used a scrolling
   modulo trick that silently never reached its own "stutter" phase within the clip's
   duration -- caught it by rendering and checking specific frames, not by reading the
   math). A fixed-pattern reveal (draw the whole shape once, wipe it in left-to-right
   over time) is easier to verify than a continuously scrolling one.

## Scripture chunking: fit content to the card, not card to a verse

At 4x original size, "one verse per card" is not a safe assumption -- a single normal
verse can run 1200-2000+ px tall depending on length and card width, which is most of
a 2160px-tall frame. `gen_overlay.py` prints a warning if a rendered card exceeds
1200px; treat that as a hard signal to split the text shorter, not as something to
just accept.

Practical approach: split scripture text into whatever chunk (a clause, half a verse,
a full short verse) renders at a reasonable card height for that video's layout --
check the actual rendered PNG dimensions before you commit to timestamps and count of
cards, the way you'd check anything else. A passage that was two cards at the old size
might need to become four at this size. This is a deliberate tradeoff Jerry has
confirmed he wants (big, legible, prominent text over a tidy small lower-third) -- lean
into it rather than trying to shrink text back down to make it fit "one verse, one
card."

## Overlay timing: use word-level timestamps, not line-level guessing

Applies to any overlay whose start/end you're deriving from the transcript --
scripture cards on both channels, and alt-edit's keyword/framework badges too. Two
rounds of Jerry feedback on main-edit videos (2026-08) bracket the right answer here,
worth reading both so the fix doesn't overshoot back the other way:

- **BreadAndCup**: cards sometimes disappeared before he'd finished reading them.
  Chunk end-times were being set from *line-level* transcript timestamps (each Whisper
  line ~3-6s covering several words) -- when a chunk's text was assembled from part of
  one line plus part of the next, the guessed window frequently ended before the
  chunk's actual last word was really spoken.
- **First attempted fix, tried on SamuelSubmission**: overcorrected by adding a
  word-count-based minimum display duration (~2.5 words/sec floor) on top of the
  line-level guess. Result: Jerry's very next feedback -- cards were now *lingering*
  on screen well after he'd moved on to unrelated commentary, sometimes several
  seconds late. A flat reading-speed floor doesn't know Jerry's actual delivery pace
  for a given passage, and it stacks with the underlying line-level imprecision rather
  than fixing it.

**The actual fix**: get real word-level timestamps and anchor each card's end to when
its own last relevant word is actually spoken, plus a small fixed buffer -- not an
independent reading-speed estimate. For a scripture card this is its last word of
verse text; for a badge it's the last word of whatever phrase/moment the badge marks.
```python
segments, info = model.transcribe(audio_path, beam_size=5, vad_filter=True,
                                   word_timestamps=True)
# each segment.words is a list of objects with .word, .start, .end
```
(`transcribe.py` doesn't request this by default -- pass `word_timestamps=True`
yourself for this purpose rather than changing the shared script's default output.)
Then, for each scripture chunk: normalize both the chunk's text and the word-level
transcript (lowercase, strip punctuation), search for the chunk's word sequence in the
timeline *near* its rough expected position (a window of about ±20s is enough to
disambiguate repeated phrases like a "he will take... he will take..." refrain without
searching the whole video), and set:
- `start` = the first matched word's start
- `end` = the last matched word's end + ~0.4s (a small fixed cushion, not a
  reading-speed floor)
Minor wording drift between the confirmed NKJV text and what Whisper actually heard
(e.g. "went to Carmel" transcribed as "went up to Carmel") will lower the match-quality
score for a chunk -- that's fine as a low-coverage warning to spot-check, not a reason
to distrust the match; as long as enough distinctive words line up, the anchor position
is still correct. After computing all chunks' times, do one forward pass enforcing that
each chunk's start is never before the previous chunk's end (cascading a shift forward
only when two chunks are genuinely back-to-back) -- this preserves chronological order
across passage boundaries and prevents a shift in one chunk from silently reordering
unrelated later content.
Short one-clause cards (e.g. "So the evening and the morning were the first day")
don't need any of this -- their natural spoken window is already the right answer.

## Layout: figure it out per video, don't assume

The single biggest lesson from these two videos: **do not place overlays by guessing
where the speaker is in frame, and do not fully trust your own visual read of a
thumbnail either.** Jerry's footage style (at least so far, both videos) is an extreme
close-up handheld walking shot where the face can occupy most of the frame and moves
around unpredictably -- sometimes filling nearly the whole frame, chin as low as ~87%
of frame height in the tightest moments seen so far. A position that looks clearly
safe in a small scaled-down thumbnail can still be wrong; video 2 caught a case where
a card's estimated-safe top edge would actually have landed on the chin.

Before finalizing any position:
1. Pull sample frames (`ffmpeg -ss <t> -vframes 1`) from the actual clipped source at
   several points *within each graphic's specific intended time window* -- not just
   generic points from elsewhere in the video, since framing can differ by scene.
2. Look at them (Read tool) and identify where the face/body consistently is NOT
   during that window.
3. **Composite the actual asset onto the actual frame and look at the result** --
   don't just eyeball coordinates against a description of where the face is. This is
   cheap (one ffmpeg overlay command + Read) and caught real problems a visual estimate
   missed. Do this for every graphic, not just the ones that seem risky.
4. Re-check with a short rendered test segment before the full encode (see
   references/ffmpeg-compositing.md).

Given how unpredictable this footage style is, video 2 defaulted to keeping
*everything* -- scripture, badges, and motion graphics -- in the bottom band (roughly
the bottom 20-25% of frame), since that was the one region that stayed clear across
every sampled frame in the whole video, rather than risking a top corner. Two elements
that are never simultaneously active can safely share the same screen position (video
2 put motion graphics in the same bottom-left slot scripture cards use, since scripture
only ever showed up in a window with no motion graphic scheduled). Treat "everything in
the bottom band, split left/right by what's active when" as the starting assumption for
this footage style; revisit only if a video's actual framing turns out to be calmer.
